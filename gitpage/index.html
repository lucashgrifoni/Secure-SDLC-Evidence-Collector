01 — Problem

Evidence exists. Proof of process does not.

Many organizations claim to practice Secure SDLC, but the evidence is scattered across pipelines, scanners, PRs, SBOMs, threat models, tickets, approvals, and attestations. Without a single model, audits turn into archaeology and releases turn into gut feel.

  1. 01

    Slow, manual audits

    Pulling evidence from multiple sources to justify a release takes days — and rarely ends up complete.

  2. 02

    Low traceability

    The scanners and the process exist, but there is no clear chain between commit, pipeline, release, and the controls actually satisfied.

  3. 03

    Weak release governance

    Production release decisions rely on informal checklists instead of an objective gate.

  4. 04

    Maturity hard to measure

    The company runs controls but cannot prove coverage, consistency, and gaps by product or team.

  5. 05

    Bureaucratic compliance

    SSDF, SAMM, or internal controls become a paperwork exercise instead of operational evidence.

02 — Value proposition

Prove the process. Don’t just detect failures.

The bundle turns scattered technical signals into a standard, auditable, release-oriented package. It does not claim "this release is secure". It states which minimum practices were proven, which were not, and how confident the evaluation is.

Evidence-driven release readiness

Releases stop depending on informal checklists and start depending on a traceable technical package with status ready, conditional, or not_ready.

Pragmatic compliance

Instead of producing parallel documents, the tool reuses evidence already born inside the engineering flow and maps it to SSDF and internal controls.

Measurable Secure SDLC coverage

Every release gets a coverage score, a confidence score, its exceptions and its gaps — with explanation, not black-box scores. compare shows what changed between two releases.

Faster audits and due diligence

One bundle with normalized records, the hash of every raw artifact, per-control evaluation, approved exceptions, and summaries — cutting manual collection time.

03 — Conceptual model

Raw -⁠> Normalized -⁠> Derived Assertion

The heart of the project is the evidence model. Three well-separated layers preserve lineage and avoid black-box scoring: the raw artifact from the source, the canonical record, and the explainable conclusion about a control.

  1. 01 raw Raw Evidence semgrep.sarif sbom.cdx.json code_review.yaml junit.xml sha256:f2e5ab32...
  2. 02 normalized Normalized Evidence evidence_type=sast_scan producer=semgrep status=passed confidence=high evidence_id=sast-8853dbef
  3. 03 derived Derived Assertion SSDF-PW.7: met SSDF-PS.3: partial SSDF-PS.2: missing rationale required

Raw Evidence

Raw artifact from the original source — SARIF, CycloneDX, JUnit, PR payload, manual attestation. Integrity preserved with a hash.

Normalized Evidence

Canonical record with type, status, timestamps, lineage, evaluated subject, and confidence. A single contract for everything.

Derived Assertion

Conclusion computed from the normalized evidence — always with explicit rationale. The score comes with explanation.

04 — Operational flow

From pipeline trigger to audit hand-off

Nine steps with chained lineage. Each step produces or consumes typed artifacts, and no release decision happens without traceability.

  1. 01

    Pipeline / Release Trigger

    Execution context: application, commit, PR, run, artifact digest, and release id.

  2. 02

    Collectors

    Source-specific adapters — GitHub Actions, local artifacts, manual attestations.

  3. 03

    Raw Evidence Reference

    Each raw artifact is recorded by path, size, and SHA-256 hash. The file itself stays where your pipeline keeps it.

  4. 04

    Normalization Engine

    Conversion to the canonical contract — SARIF, CycloneDX, SPDX, JUnit, PR payload.

  5. 05

    Control Mapping & Scoring

    Maps evidence to controls (SSDF, SAMM, internal), computes coverage and confidence.

  6. 06

    Evidence Bundle

    Consolidated JSON package — evidence, evaluations, exceptions, summary.

  7. 07

    Markdown / HTML Report

    Readable technical report and summary for humans and automation alike.

  8. 08

    Release Gate Decision

    Explicit status: ready, conditional, or not_ready.

  9. 09

    Audit Hand-off

    The same bundle feeds verify, OSCAL assessment results, an in-toto Statement, OpenVEX, and SARIF for GRC and audit tools.

06 — Scoring & status

A score without explanation is not enough

Not all evidence carries the same weight. Required evidence weighs more, some gaps block a release even with a high score, and every status comes with rationale.

release candidate

payments-api 2026.04.10

The sample release without its rollback plan and artifact signature, as the CLI scores it.

Evidence coverage82
Confidence63
not_ready missing: ORG-REL-ROLLBACK:rollback_plan, SSDF-PS.2:artifact_signature
ready

Every control is met, waived, or not applicable. No required or recommended evidence is missing.

conditional

A high control lacks required evidence, or only recommended or medium-criticality evidence is missing. Exits 0 unless you pass --fail-on conditional.

not_ready

A critical control lacks required evidence. Exits 2.

07 — Outputs

Four outputs for four audiences

One ingestion, four outputs. Machines read the bundle, engineering reads the report, stakeholders read the summary, and audit and GRC tools read standard exports of the same bundle. The first three link to the live sample.

bundle.json

Canonical evidence bundle

Versioned contract with evidence, control evaluations, exceptions, and summary. Reusable by audits and pipeline gates.

report.md

Technical report

Readable Markdown for engineering review, with lineage for every piece of evidence and rationale for every evaluation.

summary.html

Human summary

Static HTML with release status, coverage, gaps, and exceptions — ready for non-technical stakeholders.

oscal · statement · vex · sarif

Standard exports

Commands that turn the bundle into OSCAL assessment results, an in-toto Statement, OpenVEX, or SARIF for GRC and audit tools.

08 — Product security

Handling sensitive data with a secure posture

The collector lives inside pipelines that touch code, tokens, and artifacts. It ships with clear hygiene rules.

  • No secrets in logs

    Tokens, signed URLs, and sensitive artifacts are never logged.

  • Input validation

    Ingested files are validated for format and size before parsing.

  • Integrity hashing

    Every collected artifact gets a hash and provenance to preserve lineage.

  • Least privilege

    Minimal access policies for external APIs and credentials isolated per collector.

  • Manual attestations

    Treated as legitimate evidence, but weighted with lower confidence than automated signals.

  • Reproducibility

    Same input produces the same evaluation. Score and status are deterministic and explainable.

09 — Roadmap

Phased evolution, without losing the core

The CLI delivers bundle, report, and gate. Each release adds sources and standards without breaking the evidence contract. Planned work lives in the maturity roadmap.

v1.0 — shipped

Foundation

  • GitHub + GitHub Actions
  • SAST / SCA / Secrets / SBOM / Tests
  • PR approvals, threat model, rollback
  • Bundle, report.md, summary.html
  • Release gate: ready / conditional / not_ready
v2.x — shipped

Standards & AI track

  • CycloneDX 1.7, OSV, in-toto Witness predicates
  • AI evidence track (SSDF AI Profile + OWASP LLM Top 10)
  • Risk-weighted verdict + multi-VEX consumer
  • CRA 2026 + FedRAMP 20x profiles, GUAC adapter
  • Reusable GH/GitLab workflows + devcontainer
v3 – v4 — shipped

Attestations & regulation

  • in-toto, PyPI and npm attestations as evidence
  • Native Trivy JSON, IaC findings kept apart
  • SARIF export of unmet controls
  • CRA, FedRAMP 20x and CISA 2026 SBOM profiles
  • GitLab CI/CD Catalog component
Out of scope

By design

  • Hosted dashboard or trend analytics: the bundle is the product, visualization is downstream
  • Multi-tenant SaaS or telemetry
  • Running scanners or AI agents
  • A custom signing format
10 — Closing

Proof of process. Traceable. Explainable.

Releases stop depending on gut feel and start depending on chained evidence. The Secure SDLC Evidence Collector does not guarantee a secure release nor deliver automatic compliance — it shows, with lineage and rationale, which minimum practices were proven, which were not, and how confident the evaluation is.
